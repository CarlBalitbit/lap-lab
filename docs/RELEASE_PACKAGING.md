# Windows release packaging

The Windows ZIP is an end-user distribution assembled from
`packaging/windows-manifest.json`. It is separate from GitHub's source-code archives.
Only explicitly mapped files are staged; the repository and build directories are
never copied wholesale. No examples, AI configuration, developer sources/tools,
validation documentation, CI files, logs, or intermediate build products are shipped.

## Prerequisites and local use

Use PowerShell 7 on Windows with an already built Windows x64 executable. No new
dependencies are needed. Build with the documented MSVC `/MT` options and run all
mandatory circuit/race/physics/convergence validators first. Packaging does not
prove the supplied executable came from a validated build or matches `VERSION`;
use the same executable generated by that validation run.

```powershell
.\tools\test_package_windows.ps1
.\tools\package_windows.ps1 -ExecutablePath .\build\f1_track_sim.exe
```

Default outputs are `build/releases/lap-lab-<VERSION>-windows-x64.zip` and
`build/releases/SHA256SUMS.txt`. ZIP and checksum publication refuse existing
files, including races with another publisher. There is deliberately no overwrite
switch. Choose a new project-local output directory for another review build:

```powershell
.\tools\package_windows.ps1 -OutputDirectory .\build\release-review-2
.\tools\package_windows.ps1 -VerifyOnly -ArchivePath .\build\release-review-2\lap-lab-0.1.0-windows-x64.zip
```

The verifier checks against current manifest/source hashes; use the matching
release checkout and executable to verify older archives. Verification fails on
missing/unexpected entries, duplicates (including case collisions), unsafe paths,
wrong roots, size mismatches, or SHA-256 mismatches. Inputs/outputs must remain
inside the project; symlinks/junctions are rejected. The executable header must
identify a PE x64 image, but this is not cryptographic authenticity verification.

## Exact distribution

One root `lap-lab-<VERSION>-windows-x64/` contains 50 files:

- `f1_track_sim.exe`
- `LICENSE`, `CIRCUIT_DATA_LICENSE.txt`, `VERSION`, `CHANGELOG.md`
- `README.md`, `START_HERE.txt`, `RELEASE_NOTES.md` mapped from `packaging/`
- All 40 `.track` files listed explicitly in the manifest
- `tracks/README.md` and `tracks/CATALOG.md` for user-facing data documentation

Adding/removing circuits requires an intentional manifest update. The script
compares discovered lowercase `.track` files to that list; a missing or new
runtime circuit fails packaging until the manifest agrees. Unsupported files in
the repository are not copied. The manifest/scripts remain outside the ZIP.
Existing root `RELEASE_NOTES.md` and the published v0.1.0 assets are untouched.
This local ZIP changes distribution contents only; publishing a future release
and selecting its version require separate authorization. Do not replace v0.1.0.

## Determinism and failure handling

A unique clean staging folder under ignored `build/` receives only allowed inputs.
ZIP entries use ordinal ordering, fixed 2020 timestamps, and fixed attributes.
File contents are preserved byte-for-byte. The completed archive is reopened and
checked against every input hash before publication. Staging cleanup is limited
to the exact generated directory after containment/name checks.

Identical inputs on the same PowerShell/.NET compression runtime should produce
identical ZIP bytes. Different compilers can produce different executables, and
different compression implementations may produce different ZIP bytes. Runtime
versions and ZIP SHA-256 should be recorded for each real release.

ZIP/checksum publication is not a two-file atomic transaction: an I/O error or
concurrent publisher can leave a ZIP and/or empty checksum. The script fails and
never replaces or deletes those output files. Inspect any partial publication and
use a fresh output directory; do not publish artifacts from a failed invocation.
Contained staging paths and reparse checks protect normal use but are not intended
as a sandbox against an adversary concurrently changing the filesystem.

## Packaging tests and smoke verification

`test_package_windows.ps1` creates unique fixtures under ignored `build/`, packages
twice, compares ZIP hashes, verifies all 50 contents, and tests missing inputs,
unsafe paths, developer entries, duplicate entries, missing ZIP entries, altered
content, and overwrite refusal. Test fixtures are retained for review. The smoke
test launches the extracted app with redirected input and a 30-second timeout,
first quitting cleanly and then completing a Basic qualifying session using an
included circuit. It launches from a different working directory to check local
runtime discovery and export paths. No browser is opened automatically.

Manual review before publishing:

1. Verify the checksum and extract into a fresh writable Windows folder.
2. Launch `f1_track_sim.exe`, complete a qualifying and a multi-car race session.
3. Open their generated HTML reports in a modern browser; check maps, playback,
   reference selection, race lap counters, exports, and relative links.
4. Confirm only the listed distribution files are present before generating data.

Automated smoke tests do not establish browser correctness, real-car accuracy,
code signing/SmartScreen behavior, or portability to a clean Windows machine
without the build toolchain. These require additional manual/environment checks.

## Future GitHub Releases connection

A separately approved workflow can run existing mandatory validators, packaging
tests, and this packager using the executable from the same build. Upload the ZIP
and checksum as reviewable CI artifacts. A later authorized release job can publish
only these two files after matching the release tag to `VERSION`. Keep normal
failure propagation; do not suppress packaging/manifest failures. No release job,
validation-policy change, tag creation, publishing, or existing-asset replacement
is implemented by these scripts.

## Initial local verification

The native PowerShell 7.6.5 test run passed all 27 checks, including two
byte-identical builds, all file hashes, missing/unsafe/duplicate/unexpected entries,
tampered content, overwrite refusal, and extracted application version/launch and
qualifying exports. Test wall time was 8.28 s; final packaging took 0.74 s.
The local ZIP contains exactly 50 files (40 tracks), is 1,552,020 bytes, and has
SHA-256 `45669266c6c9e87b01664268589ca21dac2cde2b52422336ebcbd22ac5a6d115`.
The companion checksum and independent verification agree. The production source
hash matches its Git version. No existing release asset was replaced.

The manifest and three templates now live in `packaging/`, avoiding the existing
case-insensitive `/Release/` ignore rule. All seven packaging source files can
appear in normal Git status without ignore exceptions or force-adding files.
The repository's `.gitignore` is unchanged. A future CI checkout still requires
these inputs to be committed through the normal user-approved Git workflow.
Moving the templates changes source locations only, not archive destinations or
payload bytes. Review rebuilds use fresh output directories; previous ZIPs and
checksums remain untouched.

After relocation, all 27 tests passed again (9.13 s wall time); packaging in a
fresh review directory took 0.82 s. The rebuilt ZIP passed all 50-file content/hash
checks and has the same SHA-256 recorded above, confirming byte-identical archive
contents despite changed source paths. All seven source files appear unignored
in normal Git status. Production source, workflow, and `.gitignore` hashes match
their Git versions. No old release assets were overwritten.
